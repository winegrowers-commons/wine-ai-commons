# 基本ルール

この共有基盤は、別々の事業者が仕組みだけを共有して一緒に育てるもの。データは各自のもので、混ざらないことがいちばん大事。

## 1. まず自分の設定を読む

- 共有スキルを動かす前に、その人の 🧭 AI設定ページ（事業者名、使うDBの接続表、自分ルール、資料の上乗せ）を読む
- 接続表に無いDBを使うスキルは、推測で別のDBを使わず、止まって「このDBが未接続です」と伝える

## 2. 既定は自分で進める。人に回すのは決まった理由のときだけ

- 自分でできることは人に回さない。人に確認する・作業をお願いするのは、when-to-ask に挙げた理由（決まっていない方針、税・お金の正しさ、戻せない操作、本人しかできない操作、人が持っているもの、みんなのルールの変更）に当たるときだけ
- 事業者のデータを消す、外に送る・公開する、支払うなど、戻せない操作は、何をどこにするかを見せて承認を得てから実行する（その人が自分ルールで「確認なしでよい」と決めたものは除く）

## 3. 確かめ切ってから答える

- 製品の仕様・料金・対応状況、法令、相手の状況など、事実に当たることは、公式の情報や原本で確かめてから答える
- 「まだ確かめていません」「〜かもしれません」で終わらせない。公式の説明に書いていなければ、別の公式ページ、実際に試す、原本を開く、と手段を変えて確かめる
- 手段を尽くしても確かめられないときだけ、「確かめられなかった」と書き、何を試したか・何が残っているかを1行添える。推測で埋めない

## 4. 事業データを共有側に出さない

- GitHub の共有基盤、知識コモンズ、改善提案には、人名・金額・口座・住所・取引先名・URL・IDを入れない
- 改善提案は「どんな場面で、何が起き、どう直すとよいか」を一般化した文で書く

## 5. 学んだことを、効く範囲に振り分けて残す

直された・やり直しになった・「次からは」と言われたときは、その学びが誰に効くかで置き場を分ける。

| 効く範囲 | 置き場 |
| --- | --- |
| その人だけ（好み・書き方） | Claudeのメモリ |
| その事業者だけ（設定・事情） | 🧭 AI設定ページの自分ルール |
| みんな（スキルの誤り・足りない手順） | 改善提案DB（4のルールで一般化してから） |

## 6. 人が読むものは、資料づくりのルールに従う

ページ・報告・説明・手順書など、人が読むものを作るときは writing-for-humans に従う。人への確認やお願いも、その「人に確認・作業をお願いするとき」の形で出す。既存ページを整理し直すときは structure-reading、図を作るときは diagram を使う。
