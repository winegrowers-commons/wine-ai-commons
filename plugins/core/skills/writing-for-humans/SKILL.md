# 人間向けの資料づくり

**目的は、読み手がパッと読んで要点をつかみ、知りたければ詳細まで追えること。** 短さでも網羅でもない。

## 1. 読み手を決める

書き始める前に、読み手を1行で決める。指定がなければ既定の読み手は次の形で、「○○」に資料ごとの言葉を入れる：

> **○○に詳しい高校生**。頭の回転が速く、○○のことはよく知っている。でも、この資料の本題の前提や専門の言葉は知らない。

「○○」には、その資料を読む前に読み手が持っていてよい知識の分野を入れる。資料の本題そのものは入れない（本題を知っていたら説明が要らないので）。

| 資料 | ○○に入れるもの | 開いて説明する言葉の例 |
| --- | --- | --- |
| AIの仕組みの設計書 | AI（Claude・Notion・GitHubは使える） | MCP、Hook、マーケットプレイス |
| 防除や栽培の解説 | 農業（畑仕事の流れは知っている） | 有効成分、収穫前日数、病原菌の名前 |
| 助成金の申請メモ | 会社の仕事（雇用や給与の基本は知っている） | 支給要件、対象労働者、支給申請期間 |
| 協会の理事会資料 | ワインの業界（生産者・イベントは知っている） | 定款、決議事項、議決権 |

- この読み手が知らない言葉は、初めて出たところで短く開く（例：「MCP（Claudeを外の道具につなぐための接続口）」）。2回目からはその言葉で通す
- 単純化しすぎない。数字・固有名・条件は残す。分かりやすさは「省く」ことでなく「順番と見せ方」で作る
- 「○○」の分野の言葉は開かない。知っている人にくどく説明すると、かえって読みにくい
- 依頼に読み手が書いてあればそれに従う。🧭 AI設定ページの「資料の上乗せ」に資料ごとの読み手が書いてあれば、それに従う

## 2. 書く前に組み立てる

材料が3つ以上の出どころから来ているとき、または1画面に収まらないときは、書く前にこの順で組む。材料が多いときは先に **structure-reading** で構造を読み取る。

1. **中心の命題を1文で書く**。「この資料を読み終わると、読み手は何が分かって何ができるか」。書けないなら、まだ書き始めない
2. **章を3〜7本に決める**。命題を支える順に並べる。読み手が知っていること → 知らないこと、全体 → 部分、なぜ → 何を → どうやって
3. **材料を章に差し込む**。どの章の何のためにあるか言えない材料は、捨てるか、補足（トグル・サブページ）に回す
4. 新しい情報が来たら、末尾に足さず、効く章を書き換える

## 3. 書き方

- **1文目に結論**。ページなら冒頭の1〜2文で「何の資料で、要点は何か」が分かる
- **具体で書く**。「大幅に改善」でなく「78%→82%」。「関連のDB」でなく「出勤簿」
- **比喩を使わない**。起きていることを、そのままの言葉で書く
- **同じものは同じ言葉で呼ぶ**。1つのものに2つの名前を付けない
- **箇条書きは、本当に対等に並ぶものだけ**。理由・経緯・因果は文でつなぐ
- **表は、同じ項目で比べるものだけ**。2列しかない表は、たいてい文か箇条書きでよい
- **AIっぽい言葉を使わない**：「〜を担保」「シームレス」「包括的」「堅牢」「〜を実現」「〜の観点から」「重要なのは〜です」「〜と言えるでしょう」「まとめると」。硬い漢語の連続（「運用指針・判定基準・優先順位」）も同じ。易しい日本語の言い回しにする
- **否定で始めない**。「〜は不要」より「〜すればよい」

## 4. 詳細の置き場

| その情報は | 置き場 |
| --- | --- |
| 要点そのもの・要点を支える理由 | 本文 |
| 知りたい人だけが読む補足（だいたい1500字まで） | トグル。見出しは「何が書いてあるか」が分かる名前にする |
| 補足が長い、または他のページからも参照される | サブページ。本文には1〜2文の要約と、読む価値（何の問いに答えるか）を書いてリンクする |
| もう使わない古い案・経緯 | 「旧案と経緯」などのサブページへ。本文には残さない |

## 5. 図・表・文の使い分け

- **関係（含む・つながる・流れる・比べる）が主役なら図**。作り方は **diagram** に従う
- 同じ項目で比べるなら表、手順なら番号つきリスト、理由や因果なら文
- 図と本文で同じことを二重に書かない。図が示すことは本文で繰り返さず、図に出ていない「だから何か」を書く

## 6. 人に確認・作業をお願いするとき

人に回すかどうかは **when-to-ask** で決める。回すと決めたら、この形で書く。

**並べ方**
- 報告の冒頭に「確認・お願い（N件）」として、人にお願いすることだけを番号付きで並べる。終わったことの報告はその下に分ける
- お願いが無ければ「お願いすることはありません」と1行書く

**確認（人に決めてもらう）は1件ずつこの形**
1. **決めること**を1文。「はい／いいえ」で答えられる問いにする
2. **具体の1場面**：数字や固有名で状況を描く（「1000L出したのに985Lしか入らなかった」）
3. **AIのおすすめ**と理由1行
4. **「はい」ならどうなる・「いいえ」ならどうなる**
5. **どちらでも変わらないこと**と、**後から変えられるか**（判断の重さが分かるように）
6. **なぜAIが決められないか**を1行（when-to-ask のどの理由かを、中身の言葉で）

**作業のお願い（人の手が要る）は1件ずつこの形**
1. **どこで・何をするか**（画面の場所やボタンの名前まで。リンクがあれば付ける）
2. **なぜ人の手が要るか**を1行（本人確認、パスワード、規約への同意など）
3. **かかる時間の目安**
4. **終わったら次に何が起きるか**（「終わったら教えてください。続きは私がやります」）

**書かないこと**：AIが自分でやったことの手順、AIの内部の言葉（理由の番号や符丁）、同じお願いの言い換え

## 7. 仕上げの点検（出す前に必ず）

1. **冒頭だけ読んで**要点が分かるか
2. **見出しだけ縦に読んで**話の流れが通るか
3. **同じ内容が2か所にないか**（本文と表、図と箇条書き、本文とサブページ）
4. **前方参照がないか**（後で説明する言葉を先に使っていないか）
5. **読み手が知らない言葉が、開かれずに残っていないか**
6. 図があれば、diagram の点検も通したか
7. 人へのお願いが、冒頭にまとまっていて、AIが自分でできることが混ざっていないか
8. 古い情報・確かめていない数字が残っていないか

## 8. プロジェクトごとの上乗せ

このスキルは共通ルール。プロジェクトや資料の種類ごとの書き方（言い回し、決まった章立て、用語集）は、上乗せとして別に持つ。

- 書く前に、🧭 AI設定ページの「資料の上乗せ」欄を読み、いま書く資料に当てはまる上乗せがあれば、それを読んでから書く
- 上乗せは共通ルールに**足す**もの。共通ルールと食い違ったら上乗せを優先し、食い違いは改善提案に出す（共通ルール側を直すべきか、上乗せの例外かを決めるため）
- 上乗せの例：Vikipedia（文体のハウススタイル）、Trasageの設計資料（リポジトリの output-format.md）、協会の議事録（定款の記載事項）
