# 提案のしかた

共有のスキルやルールを変えたいときは、この形で提案にする。目的は2つ。**ほかの参加者が困らないか**を決める前に見えるようにすることと、**事業データを外に出さない**こと。

## 1. まず、本当に共有に出すものか

| こうなら | 置き場 |
| --- | --- |
| その人の好み・書き方 | Claude のメモリ。提案にしない |
| その事業者の事情・設定 | 🧭 AI設定ページの自分ルール。提案にしない |
| 共有スキルの誤り、足りない手順、ほかの人にも効くコツ | 提案にする（下へ） |

迷ったら自分ルールに置いて1か月ほど使い、ほかの人にも効きそうと分かってから提案にする。

## 2. どの層を変えるかを決める

対立の多くは、層を選べば投票せずに片づく。軽い順に考える。

1. **選べる道を足す**：今の手順は変えず、「こういう場合はこうしてもよい」を足す。誰も困らないので、まずこれを考える
2. **初期設定を変える**：みんなの初期設定を変える。今の初期設定で困っていない人の動きも変わる
3. **必須ルール（🔒）を変える**：全員に必ず効くルールを変える。破るとほかの参加者が困るものだけが必須ルール

## 3. 自分の設定で試す

出す前に、変更後の手順で自分の実際の作業を1回たどり、何が変わるかを確かめる。ほかの参加者の設定が手元にあるときは（コモンズの共有ページにある公開の設定など）、それにも当てる。

結果は、事業データを抜いて書く。

- 書く：「月次の締めで手順が1つ減る」「部門が1つしかない設定では、この確認が毎回空振りする」
- 書かない：金額、人名、取引先、自社の DB の URL や ID

## 4. 提案の形

```
タイトル：〔スキル名〕何をどう変えるか（1行）

どの層：選べる道を足す ／ 初期設定を変える ／ 必須ルールを変える
どんな場面で：（一般化した場面）
今どうなっていて、何が困るか：
どう変えるか：
自分の設定で試した結果：（楽になる点・変わる点）
困るかもしれない人：（どんな設定・使い方の人か。いなければ「思い当たらない」と書く）
戻し方：（一言で）
出どころ：（誰の気づきか。名前だけ）
```

## 5. どこへ出すか

| 提案 | 出し先 |
| --- | --- |
| 選べる道を足す、誤字・出典の更新 | GitHub のプルリクエスト（自動で取り込まれる） |
| 初期設定を変える、新しいスキル | プルリクエストにラベル「人の確認」を付ける |
| 必須ルールを変える、DBの設計図を変える | プルリクエストに「人の確認」を付け、話し合いの場でも知らせる |
| 自分で出せないとき | 話し合いの場か、GitHub の Issues に上の形で書く |

## 6. 提案を受け取って判断するとき

- まず、層を下げられないかを見る（初期設定を変える提案 → 選べる道で足りないか）
- 「困るかもしれない人」が空なら、提案した人と別の設定で試してから判断する
- 好みの違いだけなら、初期設定は変えずに選べる道として取り込む
- 誤りの直しと出典の更新は、1人からの提案でもそのまま取り込む
