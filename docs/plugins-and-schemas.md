# プラグインとDBの設計図

[全体設計](design.md) の4章の詳細。プラグインごとの中身と、それぞれが使うDBの設計図をまとめる。いまリポジトリに入っているのは core だけで、ほかはこの表に沿って順に足す。

<details>
<summary>この分け方にした理由</summary>

プラグインは入れる・外すの単位なので、**要る人・担い手・回るサイクル・知識の公開性**のどれかが違うときに分け、いつも一緒に使うものはまとめた。

- **経理と経営を分ける**：担い手（経理担当と経営者）もサイクル（毎日・毎月の記帳と、毎月・毎年の判断）も違う。経営は経理の結果を読む側
- **補助金・助成金を独立させる**：労務の助成金と設備の補助金の両方にまたがり、公募のたびに回る。制度の情報は公開されていて、生産者どうしで共有する価値がいちばん大きい
- **酒税は tank、酒類販売業の手続きは bottle**：製造者としての酒税は醸造側。小売・卸として売る側の帳簿・届出とラベル表示は販売側。免許の無い生産者は、AI設定ページで「対象外」にすれば関連スキルが動かない
- **equipment を「固定資産」と呼ばない**：固定資産は会計の分け方で、土地・建物・ソフトウェアも入り、小さな道具は入らない。使う・直すための分け方とはずれる。減価償却などの会計は accounting に任せる
- 分野をまたぐ仕事（補助金で機械を買う→経理で圧縮記帳→経営で資金繰りに反映）は、スキルどうしが次のスキルへ渡す。入っていないプラグインがあれば、そう伝えて止まる

</details>

<details>
<summary>名前のルール（IDは英語、表示は日本語）</summary>

- プラグインは `name`（ID）と `displayName`（画面に出る名前）を別に持てる。IDは小文字の英語、画面には「経理」「補助金・助成金」のように日本語を出す
- IDは一度決めたら変えない（変えると各自の入れているものが切れる）。表示名はいつでも変えてよい
- スキル・DBの論理名・プロパティにも同じルールを当てる
- 英語は辞書で引ける普通の単語にする。ローマ字は使わない

</details>

## 2. DBの設計図

共通の台帳（拠点・圃場・人・資材など）は core に置き、各分野の記録はそれを参照する。防除歴も収穫も「圃場」を参照し、給与も作業記録も「人」を参照するので、分野をまたいで足し合わせられる。

元になる場所は1か所に決める。会計はfreee、資金繰り表はスプレッドシート、栽培・醸造は将来は栽培管理のアプリ。Notionに置くのはNotionが元になるものだけで、それ以外は接続表に「どこにあるか」だけを書く。

| 分野 | DB（論理名） |
| --- | --- |
| core | 拠点 `places`、圃場・区画 `fields` / `blocks`、品種・クローン・台木 `varieties`、人 `people`、取引先・業者・行政・団体 `orgs`、資材（農薬・肥料・醸造資材） `materials`、書類 `documents`、ToDo `tasks`、改善提案 `kaizen` |
| grape | 植栽 `plantings`、作業記録 `work_logs`、観察 `observations`、防除歴 `spray_records`、土壌分析 `soil_analysis`、施肥 `fertilization`、果汁分析 `berry_samples`、収穫 `harvests`、ビンテージ `vintages` |
| tank | ロット `lots`、タンク・樽 `vessels`、セラー作業 `cellar_ops`、ワイン分析 `wine_analysis`、瓶詰め `bottlings`、委託醸造 `contract_production`、製造・移出の帳簿 `tax_ledger`、酒税申告 `tax_returns`、届出 `notices` |
| bottle | 商品 `products`、在庫 `inventory`、受注・出荷 `orders`、出店 `booths`、ラベル表示 `labels`、酒類販売の帳簿 `retail_ledger`、販売業の届出 `retail_reports` |
| labor | 雇用契約 `contracts`、出勤簿 `attendance`、給与支給記録 `payroll`、給与明細等 `payslip_files`、社保・労保の手続き `insurance_procedures` |
| accounting | 元はfreee。Notion側は 月次の締め `monthly_close`、経理ルール `accounting_rules` だけ |
| finance | 元は資金繰り表。Notion側は 経営ログ `finance_log`、投資計画 `investments`、借入 `loans` |
| grants | 制度カタログは共有知識。自社側は 申請 `applications`、補助金で取得した財産 `subsidy_assets` |
| equipment | 機器 `equipment`（種類：機械／設備／道具／デジタル機器／車両）、整備・保守 `maintenance_logs`、部品 `parts` |
| research | 参考文献 `references`、科学の値 `science_values`、科学の検証 `verifications`（どれも知識コモンズへ移す候補） |
| team | 会議・議事録 `meetings`、決定事項 `decisions`、メンバー・会員 `members`、イベント `events` |

この表はたたき台。プロパティとリレーションは、最初に作るプラグインの分から、参加者の既存のDBと突き合わせて決め、`schemas/` に置く。

## 3. プラグインに入れて配る小さな知識：制度カタログ

補助金・助成金のように、短くて毎年見直す知識は、知識コモンズではなく grants プラグインに「参照資料」として入れ、スキルと一緒に配る。

- 制度ごとに1枚：対象・要件・金額・併用の可否・締切の傾向・申請でつまずいた点・出典のURL・確認日
- スキルは使う前に公式ページで最新を確かめ、カタログと違えば改善提案を出す
- 申請した人の「ここでつまずいた」「この2つは併用できた」が改善提案で足され、次の生産者が使える
- 自社の申請記録・受給額・提出書類は共有せず、各自のNotionに残す

## 4. つなぐ先（外部連携）の3種類

| 種類 | 例 | 共有するもの | 各自がやること |
| --- | --- | --- | --- |
| 公式の接続 | Notion、freee、Google Drive、Gmail、Googleカレンダー | どのプラグインがどの接続を使うかの一覧 | 自分のアカウントでログインする |
| みんなで持つ接続 | 知識コモンズの入口、将来は気象・農薬登録情報 | 接続そのもの（1人が作れば全員が使える） | コネクタとして一度追加する |
| 自社専用の接続 | 自社で作った記録アプリなど | 作り方の型だけ | 自分の分を自分で立てる |
